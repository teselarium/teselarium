## Design principles

This project follows the next principles:

- Don't Repeat Yourself
- Keep It Simple
- Separation of Concerns
- Single Responsibility
- Modular and Composable
- Composition over inheritance
- Domain Driven Design
- Test Driven Development

UI and user experience must be coherent between the different pages and components of the application. The consistency helps to accelerate the user learning curve by making the interaction more intuitive.

Code modules and components must be coherent, simple and with well defined boundaries (see the principles mentioned before). The application design and the code design should make the developer experience easier and reduce the learning curve, and also make the application more consistent, intuitive, robust and easy to evolve.

## Conventions

AI is used in this project for accelerating development via OpenSpec (spec-driven development, not vibe coding), but AI is not authorized to create commits or push changes by it self.
Keep code readable for humans.
Don't use anonymous functions.
Don't write returns of anonymous object like anonymous list or dict (e.g. "return [a, b, ...]" or "return {a, b}"). Store the function output in a variable first and then return this variable (e.g. "variable_name = [a, b, ...]; return variable_name;").

Use explicit loops (like: for, for..of, for..in).
Reduce complexity by avoiding embedded logics and thus reducing the levels of indentation. For example, when finding more than three levels of indentation inside a function, it must be refactored by extracting some logic outside (for example in a separated function).
Avoid defining functions inside functions.

Whenever possible, prefer functional programming approach, for example creating functions that return an output without modifying the state of the input.

Use explicit return types.

Use clear naming of variables, functions, classes, methods, etc.
Prefer naming based on domain concepts (use ubiquitous language, avoid generic names like utils, helpers, manager).

Error messages must include context.

When fixing complex bugs prefer a TDD approach: write the failing test first, then fix the code.

## Vendored code

Code generated by third-party tools lives in `src/vendor/`, apart from the project's code. Today it holds only `src/vendor/shadcn/`, the components the shadcn/ui CLI generates (see its [README](../src/vendor/shadcn/README.md)).

- Vendored code is never edited by hand. It changes only by regenerating it (`npx shadcn@<version> add <name> --overwrite`), and the diff is reviewed.
- Vendored code is exempt from the conventions above and from the style lint rules. The correctness lint rules and TypeScript still apply. Prettier skips it, so it stays identical to the generator's output.
- Vendored code never imports project code. The lint enforces it.
- Project code imports vendored code through the `@/` alias, with the file extension: `import { Button } from "@/vendor/shadcn/ui/button.tsx"`. The `@/` alias is used for nothing else, so it marks third-party code. Project code otherwise keeps relative imports.
- When a vendored component needs app behavior, a project component in `src/main/` wraps it. The vendored file is not changed.
- Add a component only when a screen needs it, and list it in the zone's README.

## UI components

The app's interface is built with Tailwind CSS utilities and shadcn/ui components. Its colors, fonts, radius and spacing come from the theme tokens (`--ot-*`, see [the theme module](modules/lib/core/theme/README.md)), never from literal values. Use the shadcn component for each piece of interface, with three exceptions:

1. An element that guards the app from mods and needs real top-layer inertness stays the native element, styled with utilities. For example, the action dialog is a native `<dialog>` opened with `showModal()`.
2. When no shadcn component meets the requirement, compose a project component from shadcn parts.
3. When a native control works better (mobile, accessibility, testability), use shadcn's native-styled variant if one exists, otherwise the native element styled with utilities. For example, the Theme control is shadcn's `NativeSelect`.

Mods don't get Tailwind or shadcn. Their frames get the classless base stylesheet, which gives semantic HTML the app's look.
