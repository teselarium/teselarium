# Design

## Context

See proposal.md (Why) for motivation. The required behavior is in specs/theme and specs/mod-theme.

Current state:

- **Tokens**: `THEME_TOKENS` (`src/lib/core/theme/theme_tokens.ts`) is the only source of colors. It is built with `defineColorToken` / `defineSharedToken` and turned into CSS by `buildThemeTokenStyles()`, which writes an `@layer opentesela` block: light values on `:root, [data-ot-color-scheme="light"]`, then dark values on `[data-ot-color-scheme="dark"]`. The same text goes into the app page (a `<style>` that `main.tsx` appends at start) and into every mod frame (`THEME_FRAME_STYLES`, with the base stylesheet). The mount context gets the resolved values (`buildTheme`).
- **App styling**: two hand-written stylesheets, `src/main/app.css` (page, header, global `button`/`select`, focus) and `src/main/stage/stage.css` (stage, stage bar, issues, sandbox, action dialog). Components use plain class names. `<html>` gets `data-ot-color-scheme` from `app_theme.ts`.
- **Tests**: `theme_tokens.test.ts` decides "color token" from the `--ot-color-` prefix and checks contrast from `#rrggbb` values. `e2e/theme_probes.ts` copies three token values per scheme as hex and as `rgb()`. `e2e/mod_theme.spec.ts` names `--ot-color-accent` and `--ot-color-text`. Unit and e2e tests find elements by role, label, text, `dialog`, `iframe` and `[data-sandbox-id]`, never by the app's class names, so a restyle does not break them.
- **Lint**: `oxlint --deny-warnings` with `func-style: declaration`, `func-names: always`, `typescript/explicit-function-return-type` and `react/only-export-components` (warn, so it fails the run).
- **TypeScript**: `tsconfig.json` only references `tsconfig.app.json` and `tsconfig.node.json`. There is no `paths`, no `baseUrl` and no `strict`. Imports are relative and include `.ts` / `.tsx` extensions.
- **Packages**: shadcn 4.22, tailwindcss 4.3 and lucide-react 1.61 are the current releases. The shadcn registry could not be reached from the sandbox while this design was written, so NativeSelect's existence was not checked (see D8).

## Goals / Non-Goals

**Goals:**

- One source of design values. Tailwind's theme and shadcn's variables are derived from `--ot-*` and never define colors, radius, fonts or spacing themselves.
- A hard boundary between generated third-party code and project code, which can be seen in paths and imports and is enforced by lint config.
- No behavior change in the app beyond the look: same roles, labels, texts and DOM order for frames.

**Non-Goals:**

- Making mod frames use Tailwind or shadcn. Frames keep the classless base stylesheet. Mods never receive Tailwind's CSS.
- Compatibility aliases for the old token names.
- A class-based component kit for mods (`.ot-button`, `.ot-card`...). It is not planned. Mods get the app's look from semantic HTML and one attribute, `data-ot-variant` (D5, D9).
- Components that need JavaScript in the frame (tooltips, tabs, menus). The base stylesheet only styles native elements: `<details>`, `<dialog>`, the `title` tooltip is left to the browser.

## Decisions

### D1. File layout and the vendored zone

```
components.json                 # shadcn CLI config: aliases into src/vendor/shadcn
src/vendor/shadcn/              # generated by `npx shadcn add`; never hand-edited
  README.md                     # what this folder is, how to regenerate, the rules below
  ui/                           # button.tsx, badge.tsx, alert.tsx, native-select.tsx (D8)
  lib/utils.ts                  # cn()
  hooks/                        # only if a component brings one
src/main/
  app.css                       # Tailwind entry + shadcn aliases (D3, D4)
  stage/stage.css               # what utilities cannot express (D7)
```

`components.json` sets `aliases` to `@/vendor/shadcn/{components,ui,lib,hooks}`, `utils` to `@/vendor/shadcn/lib/utils`, `tailwind.css` to `src/main/app.css`, `iconLibrary: "lucide"`, `rsc: false` and `tsx: true`. The CLI then writes only into the vendored zone. For the CSS file, which is project code, it writes into `app.css`, and that output gets reviewed (D4).

Rules for the zone:

- It is changed only by `npx shadcn@<version> add <component> --overwrite`, never by hand. The README notes the CLI version used.
- Vendored code never imports project code. Project code imports vendored code through the alias with an explicit extension, for example `import { Button } from "@/vendor/shadcn/ui/button.tsx"`. That makes every third-party import obvious and keeps the project's import style. Project code otherwise keeps relative imports.
- When a component needs app behavior, a project component in `src/main/` wraps it.

Alternatives: `src/components/ui` (shadcn's default) mixes generated code with project components. `src/main/ui` puts generated code inside a folder that must follow the conventions. Hand-rewriting each component to the conventions turns every upgrade into a manual port.

### D2. Tooling for the zone

- **oxlint**: an `overrides` entry for `src/vendor/**` turns off `typescript/explicit-function-return-type`, `func-style`, `func-names` and `react/only-export-components`. The correctness category and every other rule still apply. The same override adds `no-restricted-imports` with patterns for `@/main/*`, `@/lib/*`, `@/App*` and relative paths that leave the zone, which enforces the one-way rule. If oxlint's `no-restricted-imports` does not support patterns, the rule goes in the README and the review checklist instead.
- **Prettier**: `src/vendor/` goes into `.prettierignore`, so generated files stay byte-identical to the CLI's output and regenerating them gives a clean diff.
- **TypeScript**: `tsc -b` still type-checks the zone. `"paths": { "@/*": ["./src/*"] }` goes into `tsconfig.app.json` (no `baseUrl`, which TypeScript 6 deprecates) and into the root `tsconfig.json` (the shadcn CLI reads it).
- **Vite and Vitest**: `resolve.alias` maps `@` to `fileURLToPath(new URL("./src", import.meta.url))`, and Vitest inherits it. The `@tailwindcss/vite` plugin goes before `react()`. Vitest does not process app CSS (only `base_stylesheet.css` is included), so jsdom tests are unaffected.

### D3. Tokens: shadcn's role vocabulary under `--ot-`

Twenty-one color tokens and eleven shared tokens, listed in specs/theme. Mapping from the old names, and where the base stylesheet and the app use each:

| Old | New | Used for |
|---|---|---|
| `color-background` | `background` | page |
| `color-text` | `foreground` | page text |
| `color-surface` | `card`, `muted`, `secondary`, `popover` | card: stage bar. muted: code, `pre`, `th`, quiet fills. secondary: plain buttons. popover: dialogs |
| (new) | `card-foreground`, `popover-foreground`, `secondary-foreground` | text on those |
| `color-text-muted` | `muted-foreground` | secondary text, disabled |
| `color-border` | `border`, `input` | separators; field borders |
| `color-accent` | `primary` | links, selection, pressed, primary button |
| `color-accent-text` | `primary-foreground` | text on primary |
| (new) | `accent`, `accent-foreground` | hover fill (shadcn's meaning) |
| `color-focus` | `ring` | focus ring |
| `color-danger` | `destructive` | errors, alerts, invalid fields |
| (new) | `destructive-foreground` | text on a filled destructive button. shadcn v4 hard-codes white there, which fails on the dark-mode red |
| `color-warning`, `color-success` | `warning`, `success` | project roles, same naming style |
| `font-body` | `font-sans` | Tailwind's name |

Values stay `#rrggbb`. The contrast test parses them, and JavaScript consumers (canvas) get plain values. shadcn's default oklch would mean a color parser in the test for no gain. `defineColorToken` / `defineSharedToken` stay as they are. The test stops relying on a name prefix and lists the color tokens explicitly, as the spec does.

Alternatives considered during explore: keep the old names and alias them in the app (A), which leaves our `accent` and shadcn's `accent` meaning different things; separate palettes for the app and mods (C), which breaks "one look"; dropping the `--ot-` prefix, which risks silent collisions with mod libraries.

### D4. `app.css`: Tailwind entry, layer order, aliases

```css
@layer opentesela, theme, base, components, utilities;   /* tokens: weakest layer */
@import "tailwindcss";
@import "tw-animate-css";

@custom-variant dark (&:where([data-ot-color-scheme="dark"], [data-ot-color-scheme="dark"] *));

/* shadcn's variables, from the tokens. On every color scheme element, so a
   section recomputes them from its own --ot-* values. */
:root, [data-ot-color-scheme] {
  --background: var(--ot-background);
  --foreground: var(--ot-foreground);
  /* ... one line per color role, plus: */
  --radius: var(--ot-radius);
  --sidebar: var(--ot-card); /* app-only roles derived here (sidebar change) */
}

@theme inline {
  --color-background: var(--background);
  /* ... shadcn's standard @theme inline block ... */
  --font-sans: var(--ot-font-sans);
  --font-mono: var(--ot-font-mono);
  --spacing: var(--ot-space-1);   /* p-4 = 4 x 0.25rem = --ot-space-4 */
}

@layer base {
  body { @apply bg-background text-foreground; font-size: var(--ot-font-size); line-height: var(--ot-line-height); }
  * { @apply border-border outline-ring/50; }
}
```

- **Layer order.** The statement at the top fixes the order before Tailwind's own statement and before `main.tsx` appends the token `<style>`. In dev, Vite injects CSS before `main.tsx`'s body runs, so without the statement `opentesela` would be declared last and would be the strongest layer. That would be harmless today, since it holds only custom properties, but fragile.
- **Aliases** go on `:root, [data-ot-color-scheme]`, not on `:root` alone. A custom property that references another is computed on the element that declares it, so `:root`-only aliases would not follow a color scheme section.
- **Spacing and radius** are derived from the tokens, so the requirement "the app takes its spacing from the tokens" holds with Tailwind's standard scale: `--ot-space-n` equals `n` units.
- `shadcn init` writes its own `:root` / `.dark` oklch blocks into the CSS file. They are replaced by the block above and never kept.

### D5. Base stylesheet: classless, shadcn-like

The base stylesheet keeps its rules: element and attribute selectors only, `var(--ot-…)` values only, no color literals (so no `color-mix()` or `transparent`), no `!important`, everything in `@layer opentesela`. Within those rules, plain elements take the look of the app's shadcn components, so the default mods and any plain-HTML mod match the app without classes:

| Element | Look (shadcn equivalent) |
|---|---|
| `button` | outline button: `inline-flex`, centered, `gap: --ot-space-2`, `min-height: 2.25rem`, padding `--ot-space-2 --ot-space-4`, `font-weight: 500`, `background` + `border`, `accent` + `accent-foreground` on hover |
| `button[type="submit"]` | default button: `primary` + `primary-foreground` and a `primary` border. Hover keeps those colors with a slight `opacity: 0.9` |
| `input`, `select`, `textarea` | input: `min-height: 2.25rem` (not `textarea`), padding `--ot-space-1 --ot-space-3`, `background` + `input` border, `muted-foreground` placeholder |
| focus on `button`, fields | `border-color: ring` plus a solid 3px `ring` outline at offset 0. shadcn's 50% translucent halo would need `color-mix()`, which the no-literal rule forbids; a solid ring is also the stronger focus indicator |
| focus elsewhere (links, `[tabindex]`) | solid 2px `ring` outline at offset 2px, as today |
| `:disabled` | `opacity: 0.5`, `cursor: not-allowed` |
| `table` | full width, no vertical borders, `border` row separators, `th` in `muted-foreground` with `font-weight: 500`, `muted` row fill on hover |
| `dialog` | `popover` + `popover-foreground`, `border`, `--ot-radius`, `--ot-shadow`, padding `--ot-space-6` |
| `code`, `kbd`, `samp`, `pre` | `muted` fill; `kbd` with a `border` |
| `a` | `primary`, `font-weight: 500`, underline offset `0.25em` |
| `h1`, `h2` | `letter-spacing: -0.025em` (shadcn's `tracking-tight`) |
| `blockquote`, `hr`, `small` | `border` and `muted-foreground`, as today with the new names |
| `[aria-pressed="true"]`, `[aria-current]` | 3px `primary` outline, as today (specs/mod-theme relies on it) |
| transitions | `color`, `background-color`, `border-color` and `outline-color` over 150ms, none under `prefers-reduced-motion: reduce` |

The page keeps `background`/`foreground`, and `accent-color` uses `primary`.

**Semantic patterns.** These map to app components, as listed in specs/mod-theme "Semantic HTML looks like the app":

| Semantic HTML | App component | Look |
|---|---|---|
| `article` | Card | `card` + `card-foreground`, `border`, `--ot-radius`, padding `--ot-space-6`, children spaced by `--ot-space-2`. Headings inside lose their top margin. shadcn's `shadow-sm` is left out: it would need a literal or a second shadow token |
| `[role="alert"]` | Alert, destructive | `card` background, `destructive` border and text, `--ot-radius`, padding `--ot-space-3 --ot-space-4` |
| `[role="status"]` | Alert, default | same box with `border` and `foreground`. Empty status elements (live regions waiting for text) are hidden with `:empty`, so they draw no box |
| `input[type="checkbox"][role="switch"]` | Switch | `appearance: none`, a pill track (2rem × 1.15rem, full radius) in `input`, `primary` when checked, the thumb drawn with `::before` in `background`, moving with a transition |
| `[aria-invalid="true"]` on fields | invalid input | `destructive` border, and a `destructive` ring on focus |
| `details` / `summary` | Accordion | `border` bottom separator, `summary` at `font-weight: 500` with padding `--ot-space-4 0`, cursor pointer |
| `[aria-busy="true"]` | loading / skeleton | `cursor: progress`, a slow opacity pulse, and a steady dimmed state under `prefers-reduced-motion: reduce` |

**Variants.** `data-ot-variant` covers what semantics cannot (specs/mod-theme "Variant attributes"). It is prefixed for the same reason as the tokens: shadcn writes a bare `data-variant` on its own components, so a mod built with its own shadcn would otherwise pick up our styles.

| Selector | Values and look |
|---|---|
| `button[data-ot-variant]` | `primary` (filled `primary`), `secondary` (filled `secondary`), `outline` (the plain look, which also turns a submit button back to outline), `ghost` (no border or fill, `accent` on hover), `destructive` (filled `destructive` + `destructive-foreground`). Filled variants dim to `opacity: 0.9` on hover, since `primary/90` would need `color-mix()` |
| `span[data-ot-variant]` | badge: `inline-flex`, padding `0.125rem --ot-space-2`, `font-size: 0.75rem`, `font-weight: 500`, full radius, 1px border. `primary` and `secondary` are filled with their role. `outline`, `destructive`, `success` and `warning` have a border and text in their role (or `border` + `foreground` for `outline`) and no fill, because those roles have no foreground pair for a filled badge |

The variant selectors are written as attribute values (`[data-ot-variant="ghost"]`), so an unknown value matches nothing and the element keeps its plain look. A bare `data-variant` matches nothing.

Alternatives considered:
- A translucent ring token (`--ot-ring-soft`) to copy shadcn's halo exactly. Rejected: it adds a token to the mod API only for a cosmetic detail.
- A class-based kit. Declined during explore: authors would have to learn and declare component names.
- Bending element meanings, such as `<mark>` for badges. Rejected: it would teach authors a semantic mistake.

### D7. Component policy and the restyle

The policy (documented in `docs/code_conventions.md`): use the shadcn component, unless (1) the element guards the app from mods and needs real top-layer inertness, in which case use the native element styled with utilities; (2) no shadcn component meets the requirement, in which case compose project components from shadcn parts; (3) a native control is better (mobile, accessibility, testability), in which case use shadcn's native-styled variant if one exists, otherwise the native element styled with utilities.

| Element | Becomes | Rule |
|---|---|---|
| Header | utilities. The `OpenTesela` heading stays an `<h1>` with that text | default |
| Theme control | shadcn `NativeSelect` inside the existing `<label>` "Theme" | 3 |
| Stage bar | card-styled `<section>` (utilities), same `aria-label` | default |
| Reload tiles / Close | shadcn `Button` (`outline` / `ghost` icon). Close shows lucide `X` and keeps `aria-label="Close"` | default |
| Issue list | `<ul aria-label="Issues">` with list styling restored. The level is a shadcn `Badge` (destructive / warning variant) holding the same level text | default |
| Load error | shadcn `Alert` (destructive) with `role="alert"`, same message | default |
| Loading | muted text | default |
| Action dialog | native `<dialog>` + `showModal()`, styled with utilities. Its buttons are shadcn `Button` | 1 |

`stage.css` keeps the rules that are about layout contracts rather than looks: `.sandbox[hidden]`, the frame's fill and `min-height: 16rem`, `.sandbox-frame-loading`, and the URL and message wrapping in the dialog. The rest moves to utilities.

### D8. NativeSelect

shadcn added a `native-select` component in late 2025, but this could not be confirmed while writing the design. The first implementation task runs `npx shadcn add native-select`. If the component does not exist, the Theme control keeps its native `<select>` with utility classes copied from shadcn's `Input` look, and nothing else changes. The component is still a real `<select>`, so `selectOption` and `getByLabel("Theme")` keep working.

### D9. Default mods as examples

The default mods are rewritten to show mod authors how a mod gets the app's look (specs/default-mods "Default mods show how to get the app's look"). Rules for all three bundled mods, the default ones and `book_list`:

- **The look comes from the theme only**: semantic HTML, ARIA states and `data-ot-variant`. Their own `<style>` holds only layout properties (`display`, `grid-*`, `flex-*`, `gap`, `width`/`min-width`/`max-width`, `align-*`, `justify-*`, `overflow*`, `margin`, `list-style`). An e2e test lists every rule outside the `opentesela` layer in each frame and fails on any color, background, border, font, radius or shadow property.
- **No classes for looks.** Elements are found by their role or by references the code keeps, not by class names.
- **Readable as examples**: a header comment states the principle and points to the theme docs. There is one named function per piece of UI (`buildModCard`, `buildFailureAlert`, `buildPermissionRow`...), and `textContent` for every value that comes from a mod or a file, never `innerHTML`. They follow `docs/code_conventions.md` as far as plain JavaScript allows (named functions, explicit loops, early returns).
- **Same texts, roles and accessible names**, so existing scenarios keep holding.

| Mod | Structure |
|---|---|
| `mod_explorer` | `<h1>` title. A `<ul>` (layout: `list-style: none`, grid) of `<li><article>`, each with an `<h2>` mod title, a `<p>` description and a `<button>` "View <title>" (its accessible name contains the title, as the tests expect). A mod that cannot be inspected is a `<div role="alert">` with the reference in `<code>` and the message. While mods load, the list region has `aria-busy="true"` and says "Loading mods…". Open errors go to a `role="status"` live region, empty until used |
| `mod_viewer` | A `<header>` with the `<h1>` title and a `<span data-ot-variant="secondary">` version badge. An `<article>` with the metadata `<dl>`, the config `<pre>`, and the permissions as a `<table>` (category, host, reason, status), where each status is a `<span>` badge, `success` "granted" or `outline` "not granted". A `<form>` for the run choices: "Run with sample tiles" is its submit button (primary), "Run without tiles" a `type="button"`. A second `<form>` for the collection address, where "Run with this collection" is a submit with `data-ot-variant="outline"`, so the page has one primary action. A typed address that is not a valid URL sets `aria-invalid="true"` on the field. Errors and "No mod was given." are a `role="alert"` / `role="status"` block |
| `book_list` | Each book is a `<li>` holding a `<button aria-pressed>` (selection, as today) around an `<article>` look with the cover, title and authors. The list keeps one `listitem` per book and "There are no books to show." as a `role="status"` |

The viewer's forms call `preventDefault()` on submit. The permission text in the table cells replaces today's single sentence, so the e2e check for `show https://upload.wikimedia.org: Shows the book covers (granted)` becomes a check of the row's cells and its `granted` badge. The spec scenario ("marked as granted") is unchanged.

For `book_list`, an `<article>` is not allowed inside a `<button>` (buttons hold phrasing content only). The selectable book stays a `<button>` with `<span>`s inside, and the card look comes from `button[aria-pressed]` plus the plain button look. The mod's layout CSS makes it a vertical block. If that doesn't look enough like a card in task 6.2, the alternative is an `<article>` holding a full-width select button.

## Risks / Trade-offs

- [Tailwind preflight resets `margin` on every element, so a modal `<dialog>` loses its UA `margin: auto` and sticks to the top left.] → Use `m-auto` (and the existing width rule) on the action dialog. An e2e test checks that the dialog is centered.
- [Preflight removes list markers, `button` backgrounds and heading sizes from the app page.] → Restyle these explicitly. The issue list gets `list-disc`. Mod frames are untouched, because preflight never enters them.
- [Styling by meaning catches elements the author meant otherwise: an `<article>` used for something that isn't a card, a `role="status"` that should be invisible, a `<details>` that isn't an accordion.] → Everything is in the weakest layer, so one unlayered rule undoes it (spec scenario "A mod undoes a pattern"). Empty status regions draw nothing. The theme docs list every pattern with how to undo it.
- [`data-ot-variant` and the semantic patterns are mod API: renaming a value or dropping a pattern later is breaking.] → The vocabulary is small and copies shadcn's names. Values are added, never renamed.
- [The switch's thumb is drawn with `::before` on a checkbox with `appearance: none`, which relies on browsers rendering pseudo-elements there (they do for checkboxes with `appearance: none`, as Pico CSS relies on).] → An e2e check covers the checked track color. The thumb is covered by the visual check in task 6.2.
- [The shadcn-like base stylesheet changes how any existing mod looks: buttons get taller and `inline-flex`, tables lose their vertical borders, submit buttons turn primary.] → Only the bundled mods exist, and they are rewritten here (D9).
- [The base stylesheet and the app's shadcn components can drift apart, since D5 is a hand copy of shadcn's look.] → Both read the same tokens, so the palette, radius and shadow never drift. Only sizes and details can, and those are checked side by side in task 6.2.
- [**BREAKING** token rename: any outside mod using `--ot-color-*` loses its colors silently.] → None are known. The proposal and the theme docs list the old-to-new mapping. A spec scenario and an e2e test check that old names are undefined, so a missed rename in the bundled mods shows up.
- [Generated code exempt from conventions grows with every component added.] → Only add components when a screen needs them. The README lists them, and the lint override is limited to style rules.
- [The `@/` alias adds a second import style.] → It is used only for vendored code (D1), which keeps the second style a marker of third-party code.
- [Radix-based components add bundle weight.] → This change adds only Button (Slot), Badge, Alert and NativeSelect. Heavier widgets come in when they are needed.
- [The vendored files are frozen at one shadcn version.] → Deliberate. Upgrades are explicit `--overwrite` runs, reviewed as diffs.

## Migration Plan

One change, no data migration. Stored theme choices are untouched. The order of the tasks keeps the build green at each step: tooling first (Tailwind, alias, lint, zone), then the token rename across lib, base stylesheet, mods and tests in one step, then the semantic patterns and variants, then the default mods' rewrite, then the app's restyle component by component. Rollback is reverting the change. There is nothing to undo in user storage.

## Open Questions

- Exact palette values may still be tuned visually during implementation (D6). That doesn't affect the specs or the tasks.
